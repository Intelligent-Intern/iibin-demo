# LCC — IIBIN Shopfloor

Vue 3 + Tailwind application, FastAPI binary IIBIN WebSocket backend, native C Python codec, Three.js valve leak-test station. Each surface has its own route and a back link to the dashboard. The machine stays alive across route changes so its guard, inserted valve and running inspection are retained. Voice commands can open/close the guard, insert/remove the valve, start or abort the inspection, and combine closing the guard with starting; “Ich habe das Ventil eingelegt” registers insertion. The insertion button moves the specimen into the fixture. Insertion/removal requires an open guard; starting requires an inserted valve and a closed guard; the guard is locked during a running or paused inspection. No application sidebar.

From this directory:

```sh
make build VOICE=1
make up VOICE=1
make down VOICE=1
```

Open http://localhost:5206/shopfloor. Docker volumes retain conversations, recordings, models, voices, cached audio and inspection reports across `make down`. First startup downloads the local models (Laya multilingual, Whisper tiny, Piper Lessac and Qwen 3.5 2B). Their status and actual compute device are visible under Administration. Network access is needed for those downloads, not for subsequent inference.

The local demo is bound to loopback and uses an explicit demo administrator identity. Employees are not created here. A production identity-provider connection is not configured.

The microphone button opens a continuous 16 kHz mono PCM16 stream over binary IIBIN WebSocket blocks (100 ms each). Speech segments are transcribed on CPU after 650 ms of silence; sustained speech is segmented after 15 seconds. The microphone stays open across replies and route navigation. Speaking again interrupts playback immediately in the browser and cancels the pending response on the server. The Stop response control does the same without closing the microphone; Mic off closes the input and output. Thread changes, disconnection and leaving the page release the microphone. Echo cancellation and noise suppression are requested from the browser. Whisper tiny processes completed speech segments, not live partial transcripts. English machine commands (with German input aliases) are matched deterministically, including close-and-start and abort; paraphrases go to Laya with separate action and FAQ selection and confidence thresholds. Whisper receives machine terminology as recognition context; common guard synonyms and recognition misspellings are normalized. Low-confidence action or FAQ predictions produce a free answer or clarification, never an arbitrary machine action. Machine interlocks are checked independently of intent recognition. Audio replies use Piper and stream cached WAV content as paced PCM blocks into a continuous Web Audio playback queue. Interrupted responses are not registered as fully played. Playback requires an initial user gesture; a visible enable-audio control handles browser restrictions. Playback completion registers the variant against the thread and queues another reviewed Piper variant without delaying the reply. Canonical FAQ variants use reviewed wording from `content/answer-variants.json`; selecting an unused variant is deterministic. Unmatched questions receive a free Qwen answer. Replies begin directly without a thinking announcement; completed sentences are synthesized with three independent, single-thread CPU Piper sessions and played in order with a bounded three-job lookahead. Playback and queued generation remain interruptible; generated reply audio is retained for replay without replacing canonical FAQ wording. Unused reviewed variants take priority. Once all variants have been played in a thread, the least recently played one is reused so voice output remains available. Audio autoplay may require a browser click. The audio cache is shared; thread deletion removes its messages and playback history, not voices or reports.

A custom voice requires your own recordings with matching transcripts. Create a voice in Administration → Voices, record at least 20 different sentences, then start training. Piper CPU fine tuning is a real background process, not instant zero-shot cloning. The initial checkpoint is downloaded from the official Rhasspy Piper checkpoint repository on first training. Quality and training duration depend on your dataset. Job failures are visible in Administration → Answer cache; full training output is retained in the data volume.

Only uploads use HTTP. All application commands, data, transcriptions and audio responses use schema-defined binary WebSocket frames. The socket accepts both `ws://localhost:5206/` and `ws://localhost:5206/ws`. The wire schema is `shared/frame.json`. The independent JS/Python packages live in sibling repositories; the old non-schema JS codecs are available only under the explicit `/legacy` entry point.

Inspection statistics are read directly from the persisted `protocol` table: total, passed, failed and the latest result. Live state questions use the current simulation state. Machine actions wait for the mounted scene instead of being discarded during initial navigation.

`make up VOICE=1` automatically enables the NVIDIA GPU for Qwen when `nvidia-smi` and Docker’s NVIDIA runtime are available. Use `make up VOICE=1 GPU=1` to require GPU access, or `make up VOICE=1 GPU=0` for CPU-only operation. Qwen uses Ollama’s automatic GPU offload; Laya, Whisper, Piper and voice training remain CPU workers. GPU use is read from the loaded model’s VRAM allocation, not inferred from the presence of a GPU. The standard `compose.yaml` remains CPU-only.

The GPU override selects the image’s bundled CUDA 12 backend: the automatic CUDA 13 backend stalled on this RTX 4090 Laptop setup. No host driver changes are required.
